# データの置き場所の方針（YAML から DB へ）

状態： 方針
現況： すべての dataset が YAML + git の正本のまま。この方針に基づく移行は未実施。

## 現在の形

- 正本は GitHub の各 repo にある構造化ファイル（YAML、Markdown）
- ダッシュボードなどのビューは、正本を取り込んで作る派生物。ビュー側の DB は正本ではない
- この形が成り立つ前提：書き手は常に1人（か1エージェント）、書き込みは1日数回、最大の dataset（本棚）でも 1,735 件

## 移行の合図

次のどれかが出た dataset から移行する。全体を一斉には移さない。

- **書き手が複数になる**：NAS の常駐 agent、外部 VM、常駐エージェント が同じデータを同時に触り、git の競合が日常化する
- **横断した問いが増える**：複数の repo をまたいだ集計が YAML + grep では苦しくなる
- **量が跳ねる**：1つの dataset が数万件規模になり、ファイル全体の書き換えが重くなる
- **家の外のアプリが直接書く**：アプリ側の書き込みが正本になる用途が出る

現時点で一番近い候補は蔵書データ等の別リポジトリ。件数と分類処理の重さが理由。

## 移行の形

- 移すのは dataset 単位。今の形の裏返しにする：DB が正本になり、YAML は DB から生成して書き戻す派生物になる
- 読み取りと git の履歴の良さは残し、書き込みだけ DB に逃がす

## DB の選択

- 本線は **PostgreSQL**。`pg_dump` でいつでも出られることが理由。標準 SQL で、置き場所を選ばない
- 小さいアプリ付属の用途は SQLite 系で十分（別リポジトリの個人アプリ（Cloudflare D1） が既存の例）

## 置き場所の選択

- 第一候補は **NAS 上の Docker + Tailscale**。月額ゼロ、誤BANの概念がなく、データが物理的に手元にある。DB のバックアップは restic → B2 の流れに乗せる
- マネージド（Supabase、Neon など）を使うのは、家の外のアプリが直接書く必要が出た場合だけ。それでも PostgreSQL なら出口は `pg_dump` で変わらない

## 順序

1. 痛みが出る
2. その dataset を PostgreSQL 化する
3. 置き場所はまず NAS、必要が出たらマネージドへ
